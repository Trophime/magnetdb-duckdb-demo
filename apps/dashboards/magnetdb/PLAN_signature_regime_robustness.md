# Plan — Signature (U/P/D) regime detection: robustness methodology for pupitre/pigbrother sync QA

Status: methodology approved (2026-08-11), revised (2026-08-12) to anchor on the reference current — parameter sweep / signal-statistics work not yet executed. One prerequisite fix already landed (see below).

## Goal

Before relying on `Signature.regimes` (the `"U"`/`"P"`/`"D"` classification of a
current/field ramp) to check whether pupitre and pigbrother data are well
synchronized after a lag correction, characterize how sensitive the
classification is to its tunable parameters (`threshold`, `window`,
sampling irregularity) on real data, and fix the robustness gaps that would
undermine a cross-system comparison.

## Background

Pupitre and pigbrother are different monitoring/control systems, generally
running at different (and in pupitre's case, variable) sampling rates, that
both measure some common fields (e.g. `Idcct1`/`Courant_A1`). The goal is to
compute the lag between the two time series and then verify the result is
actually well synchronized — not just trust a single scalar lag value.

`synchronization.py` already has (mostly unused/disabled) machinery for
exactly this: `find_best_matching_regime` matches `"U"`/`"D"` regimes between
two `Signature`s by amplitude/duration similarity and reports residual
start/end lag per match; `check_lag_reliability` flags a match as unreliable
if that residual exceeds a fraction of the run duration. It's referenced
(commented out) in `lag_test_discovery.py:688-698`.

Before trusting that check, the underlying regime detection itself needs to
be robust across two systems with different sampling characteristics. Six
gaps were identified while reviewing `signature.py`/`processing/trends.py`:

| # | Gap | Status |
|---|---|---|
| A | `threshold` is an absolute per-sample-diff magnitude, not a rate — same number means different sensitivity depending on each series' `dt`. Currently hardcoded per-source (`pupitre_threshold = pigbrother_threshold = 10` in `lag_test_discovery.py`), picked by eyeballing. | Open |
| B | `seasonal_decompose(..., period=window)` was called with `window=1` hardcoded in every caller — a no-op moving average, so no smoothing was actually happening before thresholding. | **Fixed** (this session) |
| C | No hysteresis at the threshold boundary — slope hovering near `±threshold` can chatter between labels; `Signature.compact()` only merges *consecutive identical* tags, not alternating noise. | Open |
| D | The secondary change-point-splitting rule (`trends.py:120-124`, relative slope diff `>= 0.4`) divides by the *current* sample's diff, which can be near zero right at a slope reversal — a real div-by-near-zero/spurious-split risk on noisy data. | Open |
| E | `trends_df`'s own docstring: "does not work properly if dt is not constant" — and pupitre is documented elsewhere as variable-rate (`synchronization.py:7`). `fill_small_gaps()` in the test script only patches gaps `>1.5×median` up to 30s, not general jitter. | Open |
| F | `find_best_matching_regime` does amplitude/duration nearest-neighbor matching with no positional/order constraint or uniqueness constraint — risky for a run of near-identical repeated ramps (e.g. a fast up/down oscillation block), since a wrong ramp could score as the "best" match. | Open |

**Reference current as a cleaner anchor** (added 2026-08-12): pigbrother also
records the PID controller's *reference* (setpoint) current separately from
the *actual* measured current (e.g. `Référence_A1` vs. `Courant_A1`). Since
the reference is generated by the control system rather than physically
measured, it should already be close to piecewise-linear/constant by
construction — a much better source of ground-truth regime boundaries than
bootstrapping off either noisy measured signal (see Step 2 below). This also
splits what looked like a single "lag" into two distinct things:
reference-vs-pigbrother-actual current lives in the same file/clock and
isolates the PID control loop's real physical response time;
pigbrother-actual-vs-pupitre-actual is the actual cross-system
synchronization question this methodology is for. Pupitre has no equivalent
reference/setpoint column (checked in `runlogs/pupitre.py`), so the first
comparison is unambiguous and pigbrother-only.

## Methodology

### Step 1 — Pick a small, deliberately varied test set

3-4 pupitre/pigbrother file pairs: at least one "clean" profile (long, well
separated plateaus/ramps), at least one "hard" profile (a fast
up/down-oscillating block), ideally one more from a different acquisition
session (session-to-session clock behavior isn't guaranteed to match).

### Step 2 — Extract regimes from the reference current first

The pigbrother reference/setpoint current (e.g. `Référence_A1`) is generated,
not measured, so it should already be close to piecewise-linear/constant by
construction — a much stronger candidate for establishing ground-truth
regime boundaries than bootstrapping off either noisy measured signal.

- Get its "smallest possible while well representing" piecewise-linear
  decomposition using a technique suited to that goal specifically —
  Ramer-Douglas-Peucker (minimal vertex set within a distance tolerance) or
  penalized optimal changepoint detection (PELT, via the `ruptures`
  package) — rather than tuning the existing local-diff
  `piecewise_linear_approximation` threshold, which was never designed to
  minimize segment count.
- Label each resulting segment U/P/D from its slope sign.
- Before trusting this as "clean": check the reference signal's own
  sampling/update-rate characteristics — if it steps at some control-loop
  tick rate, that could look like spurious tiny segments to either
  technique.
- Use the resulting regime windows as the known-good anchor for Step 3's
  per-regime noise-floor calibration on the *noisy* pupitre/pigbrother
  actual-current signals — replacing the circular rough-pass-then-recalibrate
  bootstrap with an externally anchored one.
- Separately, compare reference regimes against pigbrother-*actual*-current
  regimes (same file, same clock) to characterize the PID control loop's
  physical response lag on its own, uncontaminated by any pupitre/pigbrother
  clock offset — keep this distinct from the pigbrother-actual-vs-pupitre-actual
  comparison, which is the real cross-system sync question.

### Step 3 — Profile the raw signal, before choosing any detection parameter

Per source (pupitre and pigbrother separately — their noise/`dt` won't match):

- **Global stats**: `dt` distribution (mean/median/std/max gap — the direct
  read on how much the constant-`dt` assumption is violated), value
  range/units, sample count, total duration.
- **Regime split to condition the next stats on**: if reference-current
  regimes (Step 2) are available for the same time window, use them
  directly as the known-good P/U/D split. Otherwise, fall back to a
  deliberately rough first detection pass (loose threshold, no smoothing)
  on the signal itself — not to trust, just to get an initial split.
- **Per-regime stats from that split**:
  - On `P` segments specifically: diff mean (should be ≈0) and spread (MAD
    or IQR, not std — less thrown off by rare outlier samples). This is the
    actual noise-floor source for Step 4, better than hand-picking one flat
    stretch since every plateau in the run contributes.
  - `dt` mean/spread per segment — flags exactly which stretches have
    irregular sampling, i.e. where the classification is least trustworthy.
  - Duration and value-range histograms per regime type — gives a
    data-driven cutoff for the "suspiciously short segment" metric in Step 6
    instead of a guessed number.
- **Shape of the plateau-diff distribution** (histogram, not just one spread
  number) — heavy tails/occasional spikes argue for a percentile-based
  threshold (e.g. 99th percentile of `|diff|` during plateaus) rather than a
  multiple of std.

### Step 4 — Anchor the threshold search in Step 3's noise floor

Sweep `threshold` as multiples of the per-`P`-segment MAD/percentile from
Step 3, per source.

### Step 5 — Express `window` in physical time, not sample count

Decide smoothing amount in seconds (e.g. 0, 1s, 3s, 5s), convert to each
series' own sample count via its `dt` when calling `trends_df`/`trends`, so
"how much smoothing" is comparable across systems with different native
rates.

### Step 6 — Metrics, in three tiers

**Tier 1 — stability (no ground truth needed):**
- Compacted vs. raw segment count ratio (chattering indicator — gap C).
- Count of "suspiciously short" segments after compacting (cutoff from Step 3).
- How much the compacted regime *string* changes under ±10-20% threshold
  perturbation (an "elbow"-style stability check — a robust choice sits in a
  flat region of the sweep, not a single sharp optimum).

**Tier 2 — cross-system agreement (after lag correction, still no manual labels):**
- Do compacted pupitre and pigbrother regime strings have the same segment count?
- Normalized edit distance (Levenshtein) between the two compacted regime strings.
- Residual start/end lag on matched `U`/`D` segments, expressed both in
  seconds and in "number of samples" (residual ÷ each side's own `dt`).
- Reference-vs-pigbrother-actual comparison (Step 2, same clock) isolates the
  PID loop's physical lag — track it separately so cross-system sync error
  isn't conflated with genuine control-loop lag.

**Tier 3 — small manual spot-check (last, sparingly):**
Hand-pick ~5-10 visually confident transitions across 1-2 files, compare
against detected `times[]` across the parameter grid — a reality check for
Tiers 1/2, especially to catch over-smoothing (Step 5), which wouldn't show
up in Tier 1 alone.

### Step 7 — Order of operations

1. Step 2: extract reference-current regimes first, where a reference
   column is available for the run.
2. Step 3 profiling, per source — anchored on the Step 2 regime windows
   where available, falling back to the rough-pass bootstrap otherwise.
3. Sweep `threshold` (Step 4) per system using Tier 1 metrics → candidate threshold per system.
4. Sweep `window` (Step 5) holding threshold fixed → check against Tier 3 for over-smoothing.
5. **Recalibration check**: redo Step 3's per-`P` noise stats using the newly
   chosen classification instead of the rough first pass; see whether the
   candidate threshold shifts materially. If not, converged; if it does,
   iterate once more.
6. Cross-system agreement (Tier 2) across the whole small file set, not just
   the file tuned on — including the reference-vs-pigbrother-actual PID-lag
   check, kept separate from the pupitre-vs-pigbrother sync residuals.
7. Decide whether the remaining library fixes (gaps A, C, D, E, F above) are
   worth making, based on what the sweep actually showed breaking, rather
   than fixing speculatively.

## Open questions

- The "one pupitre file → several pigbrother files" correspondence case is
  confirmed to happen in practice but was explicitly deferred to a later
  step (2026-08-11) — no discovery logic exists yet for that direction
  (`FileDiscovery`/`FileSet` is currently anchored on one overview file and
  only discovers pupitre files, not the reverse).
- Where the sweep/diagnostic tooling itself should live (extend
  `lag_test_discovery.py`, a new script, or a notebook) — not yet decided.
- Whether gaps A/C/D/E/F get fixed in the shared `python_magnetrun` library
  (wide blast radius — see the existing caution in the
  `project-synchronization-redesign` memory note about `synchronization.py`
  changes) or worked around locally in the dashboard test scripts first.
- Ramer-Douglas-Peucker vs. penalized changepoint detection (PELT via
  `ruptures`) for the reference-current minimal representation (Step 2) —
  not yet tried against real data. Also unverified: whether the reference
  signal's own update/sampling rate introduces spurious segments that either
  technique would need to filter out.

## Related future work

- **`teb` as a timeseries**: `teb` currently exists only as a single
  per-record scalar mean (`record.teb = float(df_pupitre["teb"].mean())`,
  `python_magnetrun/python_magnetrun/analysis/processing.py:824`) — no
  per-timestamp extraction exists anywhere in the pipeline yet. Future plan
  (stated 2026-08-12): extract `teb` as a proper timeseries from pupitre,
  shifted using this methodology's lag computation, for magnet cooling
  modeling. This makes the sync/regime-robustness work above a hard
  prerequisite, not just a diagnostic nicety.

  **Assumption to flag when this is built**: the shift applied to `teb`
  would be borrowed directly from the current-channel lag computation, under
  the assumption that lag is a single acquisition-clock offset per pupitre
  file (shared by every channel in that file), not something that varies
  per-channel — reasonable structurally, since all columns in one pupitre
  file come off the same clock, but unlike current (which has both a
  pupitre and a pigbrother measurement to cross-check against each other),
  there is no independent pigbrother-side measurement of temperature to
  verify the applied shift against for `teb` specifically. The assumption is
  inherited, not independently validated.
